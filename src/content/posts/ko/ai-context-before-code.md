Apple Developer Academy에서 Swift 기초에 막힌 러너가 구현뿐 아니라 무엇을 생각해야 하는지까지 AI에게 바로 묻는 모습을 보았습니다. AI가 빠르게 만든 코드는 당장의 막힘을 없애지만, 학습자가 어떤 의도와 가정으로 그 결과를 판단해야 하는지는 남겨둘 수 있습니다.

이 글은 AI를 덜 쓰자는 주장이 아닙니다. 생각은 내가 하고 구현은 AI가 도울 수 있도록, AI 결과를 판단할 기준을 먼저 내 언어로 만드는 방법에 관한 글입니다. 코드를 요청하기 전에 확인해야 할 것은 프롬프트의 길이가 아니라 내가 문제를 얼마나 분명하게 이해하고 있는지입니다.

## 구현보다 먼저 정할 네 가지

### 사용자가 실제로 해결하려는 문제

요청을 기능 이름으로만 설명하면 AI는 그 기능을 빠르게 만드는 데 집중합니다. 하지만 사용자가 바라는 변화가 무엇인지 먼저 적으면 구현의 범위와 성공 기준이 달라집니다. 저는 작업을 시작할 때 “무엇을 추가할까?”보다 “이 작업 뒤에 사용자가 무엇을 더 쉽게 할 수 있어야 할까?”를 먼저 묻습니다.

### 원본 데이터와 화면의 책임

같은 정보가 여러 화면에 보이더라도 원본은 하나여야 합니다. 어떤 값이 사용자의 실제 기록이고 어떤 값이 화면에서 계산한 표현인지 구분하지 않으면, AI가 제안한 구조는 편리해 보여도 데이터 충돌을 만들 수 있습니다. 데이터의 주인과 수정 가능한 지점을 먼저 정하면 화면 컴포넌트의 책임도 자연스럽게 좁아집니다.

### 실패해도 유지되어야 하는 흐름

네트워크 연결이 끊기거나 외부 API가 응답하지 않을 때 사용자가 하던 일을 잃어서는 안 되는 경우가 있습니다. 정상 흐름만 설명한 요청은 정상 화면만 잘 만드는 답을 얻기 쉽습니다. 그래서 저는 빈 데이터, 지연, 재시도, 읽기 전용 상태처럼 실패에 가까운 조건을 구현 전에 목록으로 만듭니다.

### 제안을 평가하는 기준

AI의 답은 선택지이지 결정이 아닙니다. 기존 구조와 잘 맞는지, 데이터의 책임이 분명한지, 테스트할 수 있는지, 팀원이 설명을 듣고 유지할 수 있는지를 기준으로 제안을 채택합니다. 더 짧은 코드보다 다음 사람이 이유를 이해할 수 있는 구조를 우선할 때도 있습니다.

## 한 학습자와 의도를 먼저 적어 본 이유

C4에서 화면 코드를 수정해 본 경험은 있지만 뒷단 로직과 데이터 흐름을 연결하지 못한 한 학습자와 함께 작업했습니다. AI에게 바로 구현을 맡기기 전에 원하는 동작과 자신의 의도를 먼저 적고, 생성된 코드와 비교하게 했습니다.

그 뒤 학습자는 AI 결과에서 간과된 부분을 찾고 무엇을 더 명시했어야 하는지 설명할 수 있었습니다. 이것은 한 학습자의 한 프로젝트 맥락에서 관찰한 변화입니다. 다른 문제에서도 같은 판단을 이어갈 수 있는지는 아직 확인하지 못했습니다.

## 좋은 컨텍스트는 긴 프롬프트가 아니다

좋은 컨텍스트는 요구사항을 많이 붙이는 일이 아니라 결정에 필요한 경계를 분명히 하는 일입니다. 문제, 데이터, 실패 조건, 평가 기준을 내 언어로 먼저 정리하면 AI에게 맡길 수 있는 범위도 더 커집니다. 구현 속도를 높이는 가장 좋은 준비는 코드를 대신 써 달라고 요청하는 것이 아니라, 어떤 결과를 좋은 결과라고 부를지 먼저 결정하는 것입니다.

## 내가 생각할 부분과 AI에게 맡길 부분을 나누는 체크리스트

### 내가 먼저 정할 것

- 사용자가 겪는 문제와 이번 작업 뒤에 바뀌어야 할 상태
- 데이터의 원본, 변경 책임과 화면이 알아야 할 범위
- 빈 상태, 실패, 지연과 재시도에서 반드시 지킬 조건
- 제안을 채택하거나 버릴 평가 기준
- 지금 이해하지 못한 부분과 확인해야 할 가정

### AI에게 맡길 수 있는 것

- 이미 정한 계약을 따르는 반복 구현과 보일러플레이트 초안
- 같은 요구사항을 만족하는 여러 구현 선택지의 비교
- 내가 적은 실패 조건을 바탕으로 한 테스트 사례 초안
- 낯선 API나 패턴을 탐색할 때 확인할 용어와 문서 후보 정리

### 결과를 받은 뒤 다시 내가 할 것

- 내 의도와 다른 부분, 누락된 전제와 새로 생긴 실패 조건 표시
- 채택한 구조를 내 말로 설명하고 다음 사람이 판단할 근거 기록
- 실행, 테스트와 원본 문서를 통해 결과를 다시 확인
