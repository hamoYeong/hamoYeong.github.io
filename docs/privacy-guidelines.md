# 포트폴리오 공개 및 개인정보 가이드

> Ticket 01 공개 범위 기준
>
> 기준일: 2026-07-29

## 1. 기본 원칙

1. 공개할 수 있다는 사실과 공개해야 한다는 판단은 다르다.
2. 포트폴리오에 필요한 최소 정보만 공개한다.
3. 팀 성과와 개인 기여를 구분한다.
4. private 저장소에서 확인한 내용은 공개 가능한 요약으로 다시 작성한다.
5. 확인되지 않은 사실은 `TODO: verify`로 남기고 공개 페이지에 사실처럼 쓰지 않는다.
6. 공개 전 원본 자료의 인물, 계정, URL, 식별 가능한 데이터를 다시 확인한다.

## 2. 공개 등급

### Public

별도 승인 없이 공개 후보로 사용할 수 있다.

- 이름: 김서영
- 개발자 닉네임: Hamo
- 공개가 확인된 학력·전공의 고수준 정보
- Apple Developer Academy @ POSTECH Cohort 2026 참여
- public GitHub 저장소의 URL과 README 수준의 설명
- 본인이 작성한 공개 글과 공개 발표 링크
- 본인의 역할과 검증 가능한 기술적 기여
- 사용 기술과 공개 가능한 아키텍처 요약

### Conditional

추가 확인이나 팀 승인을 받은 뒤 공개한다.

- private 팀 프로젝트명, 기간, 스크린샷, 데모
- private 저장소에서만 확인되는 기능과 기술적 결정
- 팀 프로젝트의 정량 결과와 사용자 테스트 결과
- 설문과 인터뷰를 요약한 인사이트
- 동아리 운영 화면, Notion 화면, 실제 경기 데이터
- YouTube 조회수처럼 계속 변하는 수치
- 얼굴이 보이는 단체 사진
- 회사·학교·연구실 내부 업무의 구체적인 자료
- 이력서 PDF 원본 다운로드

### Prohibited

포트폴리오와 public 저장소에 올리지 않는다.

- 전화번호
- 생년월일
- 상세 주소
- 개인 신분증, 학생증 번호, 사번
- 비공개 이메일 또는 공개 승인을 받지 않은 개인 연락처
- secret, token, password, API key, 인증서, provisioning 정보
- private 저장소 URL과 clone 명령
- private 코드, 내부 문서, 이슈·PR 링크와 대화
- 내부 배포 URL, 관리자 URL, 운영 비밀번호
- 실제 사용자 이름, 닉네임, 계정, 경기 결과, 연락처
- 원본 인터뷰·설문 응답과 참여자를 식별할 수 있는 인용
- 팀원의 실명, 계정, 얼굴, 역할을 본인 동의 없이 공개하는 자료
- 연구 데이터와 공개 승인을 받지 않은 연구실 자료

## 3. 연락처 정책

- 기본 공개 연락처는 사용자가 공개를 승인한 이메일과 GitHub만 사용한다.
- 전화번호, 생년월일, 상세 주소는 웹에 표시하지 않는다.
- PDF에 정보가 있다는 이유만으로 웹 공개 동의가 있다고 간주하지 않는다.
- 이메일은 스팸 위험을 고려해 별도 포트폴리오용 주소 사용을 우선 검토한다.
- PDF의 과거 GitHub 계정과 현재 계정이 다르므로 최종 링크를 확인한다.

## 4. private 저장소 사용 규칙

### 허용되는 변환

private 근거:

- 특정 기능을 구현한 커밋·PR
- 내부 아키텍처 문서
- 팀의 제품 설명

공개 문장:

- `기록 화면이 저장 방식을 직접 알지 않도록 Service와 Repository의 책임을 나눴다.`
- `기기 간 상태 동기화와 센서 fallback 흐름을 구현했다.`

### 허용되지 않는 변환

- private 코드의 클래스명과 구현을 그대로 복사
- 내부 이슈·PR 제목과 번호를 목록으로 공개
- 저장소 이름이나 경로를 조합해 private URL을 노출
- 팀원의 계정과 작업 내역을 공개
- 내부 문서의 문장을 길게 인용

### 공개 전 확인

- 프로젝트명 자체가 공개 가능한가?
- 기간과 팀 규모를 공개해도 되는가?
- 기능 설명이 미출시 제품 정보를 노출하지 않는가?
- 기술 스택과 아키텍처가 팀의 공개 정책에 맞는가?
- 이미지와 데모를 팀이 승인했는가?
- 본인의 기여와 팀 전체의 기여가 분리되어 있는가?

## 5. 프로젝트 서술 규칙

모든 case study는 다음을 분리해 작성한다.

- Problem: 실제로 확인된 문제
- Context/User: 누구의 어떤 상황인지
- Role: 맡은 책임
- Action: 직접 수행한 행동
- Result: 확인된 결과와 근거
- Learning: 이후 판단이 어떻게 달라졌는지

피해야 할 표현:

- 근거 없는 `성공적으로`, `완벽하게`, `혁신적으로`
- 팀 전체 결과를 `내가 만들었다`고 표현
- CV나 저장소에 없는 역할과 수치
- 사용자의 반응을 인용한 것처럼 재구성한 문장
- private 정보가 있다는 사실을 암시하는 과도한 세부 설명

## 6. 수치와 결과

- 사용자 수, 기록 수, 조회수에는 기준일 또는 출처를 함께 둔다.
- CV에서만 확인한 값은 `CV 작성 시점 기준`으로 표시한다.
- 현재 값을 다시 확인할 수 없다면 숫자 대신 `실제 동아리 운영에 사용`처럼 검증 가능한 범위로 낮춘다.
- 팀 프로젝트의 정량 결과는 팀 승인과 산정 방법을 확인한 뒤 공개한다.
- 다운로드, 활성 사용자, 유지율 같은 KPI를 추정하지 않는다.

## 7. 이미지와 미디어

### 공개 가능 후보

- 직접 제작한 공개용 프로젝트 화면
- mock 데이터로 다시 촬영한 화면
- 개인정보를 제거한 흐름도
- 팀이 공개를 승인한 공식 스크린샷과 데모
- 본인이 촬영하고 등장 인물의 동의를 받은 사진

### 반드시 점검할 항목

- 이름, 프로필 사진, 이메일, 계정명
- 경기 결과와 순위
- Notion workspace 이름과 URL
- 브라우저 탭, 주소창, 알림
- 위치 정보와 촬영 메타데이터
- 팀원의 얼굴과 음성
- API 응답, 로그, 디버그 화면
- 저작권이 있는 영상 캡처와 썸네일

가능하면 원본을 흐리게 처리하기보다 mock 데이터로 화면을 다시 만든다.

## 8. CV와 PDF

- 현재 PDF는 전화번호, 생년월일, 상세 주소 등 웹 기본 공개에 부적절한 정보를 포함한다.
- 원본 PDF를 그대로 `public/`에 복사하지 않는다.
- 다운로드용 CV가 필요하면 공개용 버전을 별도로 만든다.
- 공개용 CV에서 제거할 항목
  - 전화번호
  - 생년월일
  - 상세 주소
  - 공개하지 않을 이메일
  - 과거 또는 잘못된 GitHub 링크
- 공개용 CV에는 작성일 또는 `웹 이력 정보가 최신`이라는 안내를 넣는다.

## 9. 저장소와 링크

- public 저장소만 `repository` 링크로 노출한다.
- private 프로젝트의 링크 필드는 비워 둔다.
- 중단된 배포 URL은 보안과 정확성을 확인하기 전까지 노출하지 않는다.
- 외부 링크는 최종 배포 전에 열림 여부와 소유자를 확인한다.
- fork나 튜토리얼 저장소는 원본과 본인 작업 범위를 명시한다.
- 라이선스가 없거나 공개 상태와 README가 충돌하면 코드 재사용과 전시 범위를 확인한다.

## 10. 공개 체크리스트

- [ ] 연락처가 공개 승인된 항목만 포함되어 있다.
- [ ] 전화번호, 생년월일, 상세 주소가 없다.
- [ ] private 저장소 URL과 내부 링크가 없다.
- [ ] secret, token, password, API key가 없다.
- [ ] 실제 사용자와 팀원을 식별할 수 있는 데이터가 없다.
- [ ] 팀 성과와 개인 기여가 구분되어 있다.
- [ ] 모든 수치에 근거와 기준 시점이 있다.
- [ ] 변경 가능한 수치는 최신 상태를 확인했다.
- [ ] 이미지에 개인정보와 내부 URL이 없다.
- [ ] 이미지·영상·폰트의 사용 권한을 확인했다.
- [ ] 공개 가능한 repository/demo 링크만 노출한다.
- [ ] 확인되지 않은 내용은 공개 문장에서 제거하거나 `TODO: verify` 상태로 남겼다.

## 11. 콘텐츠 작성 워크플로

1. source와 근거 위치를 내부 작업 메모에 기록한다.
2. 공개 문장은 필요한 수준으로 요약한다.
3. 개인 기여와 팀 기여를 분리한다.
4. private 정보와 개인정보를 제거한다.
5. 수치와 링크를 재검증한다.
6. 이미지에는 mock 데이터를 적용한다.
7. 팀 프로젝트는 필요한 공개 승인을 받는다.
8. production 빌드에서 draft와 conditional 콘텐츠가 노출되지 않는지 확인한다.
